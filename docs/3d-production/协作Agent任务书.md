# 《德扑酒馆》3D 制作：协作 Agent 任务书

## 一、任务目标

为《德扑酒馆》的 3D 游戏制作整理基础资料，让负责开发和建模的主 Agent 能直接知道：

- 现有项目包含哪些场景、角色、道具和撤离路线。
- 每项内容有哪些可用素材、缺少什么。
- 素材与当前玩法是否对应。
- 后续逐项验收时，应检查什么。

**本次只整理资料，不开发功能、不制作模型、不改变玩法。** 框架搭建、Blender 建模、规则迁移和技术决策由主 Agent 负责。

## 二、项目方向与协作边界

用户已确认的方向：

- Blender 制作资产，Godot 实现桌面游戏，先验证 Mac，再交付 Windows 版本。
- 第一人称在房间内有限自由探索；入座后采用牌桌视角；房间通过门和短过渡连接。
- 美术向原始场景参考图的写实氛围靠拢。
- 撤离做到可抵达入口、条件判断和短离场演出。
- 采用自制及许可明确的免费可商用素材。
- 先完成一条高完成度可玩流程，经用户验收后推广到全部场景。

你的工作是提供准确的资料和可执行的检查步骤，不替主 Agent 决定模型规格、技术架构或玩法变化。

## 三、任务 1：清点现有美术素材

### 具体做什么

清点以下目录中的场景图片、视频、Blender 文件、扑克牌及其他游戏素材：

```text
assets/scene-plates/
assets/videos/
assets/blender/
Godot/
```

### 怎么做

1. 先列文件名、路径、格式和用途；排除 `.godot/` 等缓存，不把导入缓存当作源素材。
2. 场景图必须打开查看，不能仅凭文件名判断内容。确实无法查看时标注“未查看”。
3. 图片记录尺寸；视频能读取时记录时长和分辨率，读取不了写“未核验”。
4. 相似或重复素材归组，区分主场景、局部视角、弹窗、路线画面。
5. 连续系列可以归组，例如 52 张扑克牌，不必每张写长说明；归组时记录数量和覆盖路径。
6. Blender 文件只确认存在及已有说明，不能把“存在模型”写成“已达到游戏可用标准”。
7. 当前使用关系应检查配置和代码引用；未找到引用不等于确定未使用。

### 交付：`assets.csv`

至少包含以下字段：

| 字段 | 说明 |
|---|---|
| 素材编号 | 本次清点用的唯一编号 |
| 相对路径 | 相对于项目根目录，必须验证存在 |
| 类型 | 场景图、视频、模型、牌面等 |
| 数量 | 单文件填 1，系列按实测数量填写 |
| 尺寸／时长 | 实测值或“未核验” |
| 画面内容 | 实际看到的主要内容 |
| 对应玩法 ID | 能确认才填写 |
| 对应关系状态 | 已确认、推测、待确认 |
| 当前使用证据 | 配置或代码位置；找不到写“未发现直接引用” |
| 3D 制作参考价值 | 构图、材质、道具、灯光等 |
| 备注 | 重复、旧版本、命名疑点等 |

### 期望结果

负责建模的人能按表找到参考素材，明确哪些对应关系有证据，哪些需要确认。

## 四、任务 2：整理游戏内容与场景对应关系

### 具体做什么

以当前代码为依据，整理：

- 4 种酒馆环境。
- 4 套牌桌关卡。
- 8 位对手。
- 19 项物品。
- 16 条酒馆专属撤离路线。
- 通用撤离及舍弃现金、舍弃贵重物分支。

以上数量是此前检查的参考值，需要自行核对；不一致时报告差异，不强行凑数。

### 怎么做

优先读取：

```text
src/data.js
src/game.js
src/main.js
scenes/
assets/videos/manifest.json
```

分别整理以下表格：

| 内容 | 必须列出的信息 |
|---|---|
| 酒馆 | ID、名称、背景素材、服务、专属路线 |
| 牌桌 | ID、名称、解锁关系、对手、特殊规则、奖励 |
| 对手 | ID、名称、所属牌桌、已有性格描述、角色素材是否存在 |
| 物品 | ID、名称、用途、使用阶段、是否建议独立实体模型及理由 |
| 路线 | 所属酒馆、配置键、实际 ID、条件、费用、参考图、映射疑点 |

每组结论附代码或配置证据位置。对于“是否需要独立模型”等制作判断，明确标为建议，不伪装成已确认要求。

### 特别注意

- 四种酒馆环境与四套牌桌关卡是两个维度，不能直接理解为一间酒馆只对应一套牌桌。
- `specialRoutes` 中的配置键与实际 `route.id` 可能不同，必须分别记录。
- 有些路线图片属于旧命名，不能擅自重命名或强行绑定。
- 旧设计文档存在“两套牌桌、不支持全押”等过时描述。与现行代码冲突时列出差异，不修改代码或替项目决定新规则。
- 找到一段逻辑不等于实跑通过，不宣称功能已经验证完成。

### 交付：`content-map.md`

### 期望结果

开发者能够直接用它安排资产制作和功能迁移，同时看到明确的待确认事项。

## 五、任务 3：整理现有素材许可证

### 具体做什么

检查项目内已经存在的第三方素材许可，尤其是扑克牌、字体、模型、音频等。

### 怎么做

1. 只检查项目中现有的 `LICENSE`、`README`、作者声明和来源记录。
2. 记录许可证覆盖的具体目录或文件。
3. 分开列出商用要求、署名要求、再分发要求，以及没有明确证据的部分。
4. “免费”“可下载”“项目里已有”都不能作为可商用的证据。
5. 自制或生成素材只有在记录明确时才这样标注；其余写“来源待确认”。
6. 只摘录和归纳许可原文中明确的条件，不作没有依据的法律结论。
7. 不联网寻找替代素材，不下载，不购买。

### 交付：`licenses.md`

至少包含：

```text
素材／素材组
覆盖路径
来源或作者
许可证名称
本地证据位置
明确写出的使用条件
未确认事项
```

### 期望结果

能看出哪些素材已有许可证据，哪些仍需补充来源与授权信息，暂不进入正式发行素材清单。

## 六、任务 4：编写可重复使用的验收清单

### 具体做什么

为以后逐场景检查提供操作步骤。现在只编写清单，**不把尚未完成的 3D 功能标为通过**。

### 怎么做

每条检查包含：

```text
检查编号
适用场景
前置条件
操作步骤
预期结果
实际结果
通过／失败／未执行
证据位置
```

默认状态为“未执行”，实际结果和证据位置留空。

覆盖以下内容：

- 场景能否进入和返回。
- 角色是否卡住、穿墙或出生在错误位置。
- 可交互物件是否有提示，能否隔墙误操作。
- 面板打开与关闭后的鼠标、移动状态是否正确。
- 入座、离座、牌面和金额是否清楚。
- 道具使用条件、库存和消耗是否一致。
- 撤离条件、扣款、损失说明和结算是否一致。
- 成功／失败后能否进入下一步。
- 保存与恢复是否保持状态。
- 缺贴图、模型闪烁、错误碰撞等画面问题。

通用检查可以共用，但要明确适用场景；特殊路线和牌桌规则需要单列检查。只写已有计划明确包含的功能，不增加战斗、驾驶或联网等新范围。

### 交付：`acceptance-checklist.md`

### 期望结果

其他人拿到检查版本后，可以照步骤操作并记录结果，不需要重新理解整个项目。

## 七、任务 5：交付摘要与自检

### 交付：`README.md`

说明：

- 本次扫描范围和未扫描范围。
- 素材和游戏内容数量。
- 五份交付文件的用途。
- 最重要的缺失素材和映射疑点。
- 哪些结论已核实，哪些仍待确认。
- 建模或开发 Agent 下一步可以直接使用哪些结果。

将待确认事项集中列出，附对应证据和影响，不替主 Agent 作决策。

### 交付前自行检查

1. 表格中所有已填写的真实文件路径都存在；建议新增的资产另列，不混入现有文件。
2. 内容数量与当前代码一致，差异有说明。
3. 不把推测写成已确认。
4. 不把计划中的功能写成已完成。
5. 所有待确认事项集中列出，避免散落在表格里。
6. 输出文件可读，CSV 使用 UTF-8 编码，包含逗号或换行的字段正确转义。
7. 只修改授权输出目录，没有触碰代码、模型或原始素材。

最终应有五份文件：

```text
docs/3d-production/inventory/
├── README.md
├── assets.csv
├── content-map.md
├── licenses.md
└── acceptance-checklist.md
```

## 八、执行顺序与工作边界

建议顺序：阅读项目说明与现行内容配置 → 素材清点 → 内容映射 → 许可证整理 → 验收清单 → 汇总自检。

- 先读取适用的 `AGENTS.md`。
- 只允许新增或修改 `docs/3d-production/inventory/` 内的文件；目录不存在时可以创建。
- 不改 `src/`、`scenes/`、`Godot/`、模型、原始素材或本任务书。
- 不安装工具，不批量重命名，不删除，不提交或推送 Git。
- 不启动游戏编辑器，不修改导入设置，不生成模型或贴图。
- 不决定引擎架构、模型精度、美术风格或玩法修改。
- 遇到不确定项，记录证据和问题，交给主 Agent 判断。

**完成后发回：交付文件路径、统计结果、最重要的疑点，以及自检结果。**
